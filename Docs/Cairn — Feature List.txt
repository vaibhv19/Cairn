Cairn — Feature List
PROJECT NAME: Cairn (Distributed Cache Service — Spring Boot/Java build)
Stack: Java + Spring Boot + java.util.concurrent (ConcurrentHashMap, ReadWriteLock, ScheduledExecutorService)
Core Differentiator: Same custom in-memory cache engine as Shard, but concurrency safety is implemented via Java's true multi-threaded parallelism rather than Python's GIL-limited model — the deliberate point of comparison between the two twins

MVP (build first)

In-Memory Key-Value Store Core — thread-safe map (ConcurrentHashMap or a custom lock-striped structure) supporting SET/GET/DELETE/EXISTS, single-node only, no persistence
Pluggable Eviction Policies — LRU and LFU implemented as a Strategy-pattern interface with swappable Spring beans, selectable per cache instance
TTL Expiry — per-key expiration set at write time; active expiry via ScheduledExecutorService background sweep, passive expiry checked on access
Concurrency Safety — correctness under genuine concurrent multi-threaded access (not just interleaved single-threaded execution); read-write locks or lock-free structures where appropriate — this is the sharper test of the concurrency model, since Java threads run in true parallel unlike Python's GIL-limited threading
Client-Facing API — SET/GET/DELETE/EXISTS/EXPIRE/TTL exposed via Spring Boot REST controllers
Core engineering: eviction and expiry logic must stay correct under real concurrent load — no silently corrupting cache state, no evicting or expiring the wrong key due to a race condition

Phase 2 — Sharding & distribution (scoped honestly, not a full Redis Cluster reimplementation)

Consistent Hashing Ring — routes keys deterministically to one of several cache-node instances
Routing Layer — a thin proxy or client-side hashing component that resolves which node owns a given key
Static Node Membership — node list comes from Spring config; explicitly scoped as "consistent-hashing based static sharding, not dynamic cluster membership or a gossip protocol"
Rebalancing Behavior — documented (and at minimum partially implemented) behavior for what happens to key ownership when a node is added or removed

Phase 3 — Invalidation strategies & metrics dashboard

Cache Invalidation Strategies — explicit invalidate command, write-through vs. write-back semantics, TTL-based passive invalidation
Metrics Collection — hit/miss ratio, eviction count, per-node memory usage, latency percentiles (Spring Boot Actuator is a natural fit here)
Metrics Dashboard — aggregates across nodes; useful for comparing eviction-policy configurations against each other (e.g. "does LFU reduce miss rate vs LRU for this access pattern?")
